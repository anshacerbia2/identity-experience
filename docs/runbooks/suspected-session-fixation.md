# Runbook: Suspected Session Fixation

Session fixation is an attacker planting a session identifier in a victim's browser before the victim
signs in, so that the attacker holds the identifier of the session the victim then authenticates.
Login cross-site request forgery is its mirror: the victim's browser is signed in as the attacker.
This runbook is for a report or a signal that either happened.

## The controls in place

OWASP: "The session ID must be renewed or regenerated by the web application after any privilege level
change within the associated user session" [R1]. Each control below is in the code and under test.

| Control | Where | Test |
| :-- | :-- | :-- |
| Every sign-in issues a new 256-bit identifier, and ends the session the browser held before | `bff/src/auth/routes.ts`, `/auth/callback`; `bff/src/session/sessions.ts` | `auth.test.ts` "issues a new session identifier at sign-in and ends one planted before it" |
| The cookie is `__Host-` prefixed: `Secure`, `Path=/`, no `Domain`, so a neighbouring subdomain cannot set or overwrite it [R1] | `bff/src/http/cookies.ts` | `auth.test.ts` "sets the session cookie HttpOnly, Secure, SameSite=Lax, __Host-…" |
| The callback is bound to the browser that started the sign-in by a second cookie, `__Host-ident_login`, consumed once | `/auth/callback` | `auth.test.ts` "a callback in a browser that did not start the sign-in", "a replayed callback" |
| The store keys rows by the SHA-256 of the cookie, so a copy of the table is not a set of cookies | `bff/src/session/store.ts` | `containment.test.ts` "the session store's rows … hold no token and no cookie value" |
| `state`, `nonce` and PKCE `S256` are checked on every callback | `bff/src/auth/oidc.ts` | `auth.test.ts` "refuses …" |

So a planted identifier never becomes an authenticated one. A report of fixation is first a question:
which of these failed, or was it something else that looks like it?

## Signals

| Log line (`msg`) | Field | What it may mean |
| :-- | :-- | :-- |
| `sign-in refused` | `reason: no sign-in in flight in this browser` | A callback arrived without the login cookie: a code and state delivered to another browser, which is the login CSRF attempt the binding stops |
| `sign-in refused` | `reason: state mismatch`, `the sign-in expired or was already completed` | A replayed or forged callback |
| `csrf rejection: origin`, `csrf rejection: token` | `origin` | A cross-site request carrying the session cookie |

Any burst of these from one origin is worth an incident even with no report: OWASP asks applications to
"detect both scenarios based on the number of attempts to gather (or use) different session IDs and
alert and/or block the offending IP address(es)" [R1]. The BFF logs no client address
(`trustProxy: false`); the address is the ingress's log, joined on time and path.

## Steps

1. **Establish whose session.** Get the person's Principal and the time. Ask what they saw: a name in
   the frame that was not theirs is login CSRF; an action they did not take is a stolen or fixed
   session.
2. **End that person's sessions, all of them.**
   - In the Admin Portal, the Principal's page, "End every session"
     (`POST /v1/principals/{principal_id}/sessions:terminate-all`). This ends the Keycloak sessions.
   - Then, as the serving role, delete their BFF sessions:
     `DELETE FROM sessions WHERE subject = '<keycloak subject>'`. Their browsers answer `401` at the
     next request.
   - If the attacker's own account was signed in to the victim's browser, end that account's sessions
     the same way and suspend it.
3. **Look at what the session did.** The Principal's Events section in the Admin Portal lists sign-ins
   and admin changes from the kernel's record. Each command through the BFF reached the Identity
   Control API with its `X-Administrative-Reason`, which the API records.
4. **Check the controls held.** Run the BFF tests on the deployed commit: `pnpm --filter
   @identity-experience/bff test` with a throwaway PostgreSQL. Check the deployed response headers:
   the session cookie `__Host-ident_session` with `HttpOnly; Secure; SameSite=Lax; Path=/`, and the
   security headers of TDD-001. A proxy that rewrites `Set-Cookie` or serves the BFF on another name
   breaks the prefix.
5. **Only if the store itself may be exposed,** rotate the session key, which signs everyone out:
   - stop every replica;
   - as the serving role, `DELETE FROM sessions; DELETE FROM login_states;`;
   - set a new 32-byte `IDENTITY_EXPERIENCE_SESSION_KEY` in the secret manager;
   - start the replicas.

   Do the delete. A row sealed under the old key does not open under the new one, and a request that
   presents it fails with `500` rather than being signed out (`Sealer.open` throws). A copy of the
   table alone grants nothing: rows are keyed by the cookie's digest and the tokens are sealed under a
   key the database never sees.

## Verify

- The person signs in again and sees their own name.
- No `sign-in refused` or `csrf rejection` lines from the attacker's origin after the response.
